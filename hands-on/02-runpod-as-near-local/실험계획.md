# RunPod ephemeral GPU 실험계획

작성일: 2026-10-17 (Asia/Seoul)  
상태: 2026-10-18 기본 범위 실험 완료 — 실측 결과는 [결과 보고서](reports/results.md), 청구 확정은 대기 중

> 이전 대화의 사용자 요구사항을 바탕으로 재구성한 계획이다. 이전 assistant 답변은 대화 조회에서도 참조 표시로만 반환되어 원문 및 당시 H1~H5의 문구는 확인하지 못했다. 아래 가설과 기준은 이번 문서에서 제안한 것이며, 기존 답변의 정확한 복원본은 아니다.

## 1. 목적과 범위

로컬에서 코드 작성·에이전트 추론·분석을 수행하고, GPU가 필요한 순간에만 RunPod Pod를 생성해 SSH로 작업한 뒤 결과를 보존하고 삭제한다. 모델처럼 크고 개수가 적은 파일은 RunPod network volume에 두고 S3 호환 API로 접근하는 사용 패턴을 평가한다.

검증할 핵심은 “API 요청이 빠르다”가 아니라 **사용 의도 발생부터 첫 유효 GPU 결과까지의 시간**, **성공한 작업당 총비용**, **삭제 후 재현·복구 가능성**이다. 여기서 “로컬 GPU처럼”은 원격 명령 실행과 파일·환경 관리의 편의성을 뜻한다. 로컬 CUDA 장치로 투명하게 연결되는 기능을 전제하지 않는다.

이 문서는 실험 설계다. 사용자의 실행 지시에 따라 기본 범위를 수행했으며 실제 진행 내역과 가설 판정은 `records/`와 `reports/`에 남겼다. 아래 기록 템플릿은 설계용이며 실제 판정은 결과 보고서를 기준으로 한다. 1 GPU, 단일 사용자, 큰 파일 소수 개를 1차 범위로 삼고 다중 GPU·분산학습·Serverless는 제외한다.

**첫 실험의 범위:** 고정 추론 작업 하나로 생성 → 실행 → 결과 회수 → 삭제 → 새 Pod에서 재실행을 검증한다. 기본 구현은 작은 실행 스크립트, 실행 원장, 타임아웃, 별도 정리 감시기로 한정한다. 학습 재개, 대용량 확장, 저장소 3종 비교, 묶음형 정책은 기본 결과를 본 뒤 필요한 경우에만 진행한다. 아래 CLI와 디렉터리 구조는 확장 방향이며 처음부터 전부 구현하지 않는다.

**GPU 인스턴스 제약:** NVIDIA GeForce RTX 5090 및 그보다 시간당 GPU 임대 단가가 저렴한 GPU만 사용한다. 실험 시작 전 실제 제공 중인 RTX 5090의 단일 GPU On-demand 견적 하나를 골라 데이터센터·통화·취득시각·출처와 함께 기록하고, 해당 단가를 이번 실험의 고정 상한으로 사용한다. 선택 GPU는 다른 데이터센터여도 되지만 동일 통화·On-demand 기준으로 생성 직전 단가가 상한을 충족해야 한다. 기준 견적을 확인할 수 없거나 허용 GPU의 재고·VRAM이 부족하면 실행을 보류하거나 워크로드를 축소하며, 더 비싼 GPU로 대체하지 않는다.

## 2. 확인된 기능과 검증 경계

공식 문서를 2026-10-17에 확인했다. 문서상 지원과 실제 계정·지역에서의 동작을 구분한다. 실행 전 문서를 다시 확인하고 관련 설정과 가격을 기록한다.

| 항목 | 문서에서 확인한 내용 | 실험에서 확인할 사항 |
|---|---|---|
| 생성·삭제 | Pod 관리 문서는 생성·조회·삭제 경로를 제공한다. [공식 관리 문서](https://docs.runpod.io/pods/manage-pods) | 선택 API/CLI 버전의 필드, 비동기 상태, 오류·타임아웃·삭제 확인 방식 |
| 영속 저장소 | Network volume은 Pod와 독립적이며 Pod 종료 후 유지된다. 일반 network volume의 위치는 GPU 선택을 제한한다. [공식 저장소 문서](https://docs.runpod.io/storage/network-volumes) | 선택 데이터센터의 GPU 재고, 실제 마운트 위치, 재생성 후 파일 접근 |
| S3 접근 | Network volume의 파일에 Pod 없이 접근하는 S3 호환 API가 있으며 지원 데이터센터가 제한된다. 제어 API 키와 S3 키는 별개다. [공식 S3 문서](https://docs.runpod.io/storage/s3-api) | endpoint·region·volume ID, 업로드·다운로드·목록·무결성, SDK 호환성 |
| SSH | Basic SSH는 SCP/SFTP를 지원하지 않는다. Full SSH는 public IP 등 조건이 필요하다. [공식 SSH 문서](https://docs.runpod.io/pods/configuration/use-ssh) | 비대화형 명령, 종료코드 전달, 재접속, IDE·파일 전송에 필요한 기능 |
| 과금 | GPU 가격은 배포 시 확인해야 하며, Pod 삭제 후에도 남긴 network volume 비용은 발생한다. [가격](https://docs.runpod.io/pods/pricing), [과금](https://docs.runpod.io/accounts-billing/billing) | 실제 청구 시작·종료, 저장소 산정 기준, 세금·외부 서비스 비용 |

S3 호환은 AWS S3 전체 기능과 동등하다는 뜻이 아니다. 현재 문서는 multipart upload를 안내하지만 versioning·presigned URL·bucket policy는 미지원으로 표시한다. 재시작 후 전송 재개, 동일 파일의 S3/마운트 동시 수정, 원자적 공개, 일관성 보장은 가정하지 않는다. [호환성 표](https://docs.runpod.io/storage/s3-api#s3-api-compatibility-reference)

자동 TTL 삭제, 계정별 hard budget cap, 생성 요청의 멱등성 키, 세밀한 자격증명 범위는 이 설계에서 RunPod 기본 기능으로 단정하지 않는다. 지원 여부를 확인하기 전에는 자체 제어기로 구현할 설계 항목이다. Global volumes 등 별도·베타 저장소는 1차 비교에 포함하지 않는다.

## 3. 가설 H1~H5

아래 숫자는 서비스 보장이나 측정값이 아닌 **사전 등록할 초기 목표**다. Phase A 이후 본 실험 전에 한 번 조정할 수 있으며, 변경 이유를 남긴다.

기본 실험은 H1·H2·추론 재현성·기본 정리를 탐색적으로 평가한다. 선택 실험을 하지 않은 가설 항목은 미실시로 표시하고 판단을 유보한다. 적은 표본으로 일반적인 신뢰성이나 성능을 보장하지 않는다.

| 가설 | 비교 및 측정 | 초기 통과 기준 |
|---|---|---|
| H1: 준비된 환경이라면 매번 생성해도 대기시간이 실용적이다. | 고정 W1로 새 Pod 3회. 작업 확정→추론 직전 준비 완료와 작업 확정→첫 유효 결과를 각각 측정 | 3회 모두 준비 완료까지 5분 이내, 준비시간 중앙값 180초 이하를 초기 목표로 삼고 첫 결과 시간은 별도 보고 |
| H2: 에이전트 추론 동안 GPU를 삭제하면 총비용이 줄어든다. | 같은 작업·대기시간에서 유지형과 ephemeral 비교. 재생성·실패 비용 포함 | 대표 대기 패턴에서 성공 작업당 비용이 30% 이상 감소하고, 전체 완료시간 증가가 20% 이하 |
| H3: 큰 파일 소수 개는 영속 저장소 재사용으로 전송 낭비를 줄인다. | 매회 원격 다운로드와 network volume 직접 읽기, 임시 디스크 복사 비교 | 재사용 방식 중 하나가 반복 실행 준비시간 중앙값을 30% 이상 줄이고 모든 검증 파일 SHA-256 일치 |
| H4: 고정 환경과 명시적 상태 저장으로 새 Pod에서 재현·재개할 수 있다. | 기본: 이미지 digest·코드 commit·모델 hash·seed를 고정해 새 Pod 3회 추론 재현. 선택: 학습 중단 복구 3회 | 추론 결과 오차가 사전 정의 허용치 이내, 수작업 환경 수정 0회. 학습 복구는 실시한 경우에만 별도 판정 |
| H5: 실패가 있어도 자원 누수와 데이터 손실을 제한할 수 있다. | 기본: SSH 끊김·제어기 중단 각각 1회. 생성 응답 유실·업로드 실패·API 장애는 선택 실험 | 시험한 장애에서 제어기 복구·API 접근 가능 시점부터 5분 내 잔여 Pod 0개, 비용 상한 규칙 위반 0건, 확정 산출물 손상 0건 |

H5의 API 장애 구간에는 삭제 지연의 유한 상한을 보장할 수 없다. 장애 지속시간, 초과비용, 수동 개입을 별도 보고하고 “상한 보장 성공”으로 처리하지 않는다.

## 4. 아키텍처

```text
로컬 PC
 ├─ 에이전트: 추론, 코드 작성, 결과 분석 (원칙적으로 GPU 미할당)
 ├─ 실행 제어기: 사전점검 → 생성 → 연결 → 실행 → 보존 → 삭제 확인
 ├─ 실행 원장: run_id, Pod ID, 상태, 만료시각, 비용, 재시도
 └─ 별도 감시기: 원장과 실제 Pod 목록 대조, 만료 자원 정리
        │ 제어 API                    │ SSH / S3 호환 API
        ▼                             ▼
 RunPod 임시 GPU Pod             RunPod network volume
 ├─ 고정 컨테이너 이미지          ├─ models/<content-hash>/
 ├─ 고정 commit의 실행 코드       ├─ datasets/<content-hash>/
 ├─ GPU 연산                     └─ runs/<run_id>/
 └─ 폐기 가능한 로컬 캐시                │
                                  로컬 또는 독립 저장소 백업
```

기본 경로는 network volume을 생성 시 연결한 Pod에서 모델을 읽는 방식이다. S3 API는 Pod를 켜지 않고 사전 업로드하거나 결과를 회수하는 경로로 사용한다. 같은 저장소를 마운트와 S3 두 경로에서 동시에 수정하지 않는다.

비교 경로로 network volume 파일을 Pod 임시 디스크에 복사해 읽는다. 복사 시간과 임시 디스크 비용까지 포함한다. 복사 대상의 디스크 종류·용량·실제 경로는 실행 전 확인한다. `/workspace`라는 이름만 보고 임시 디스크라고 판단하지 않는다.

제어기 인터페이스 예시는 다음과 같다. 이는 **구현할 로컬 도구의 명세**이며 RunPod의 실제 명령이 아니다.

```text
gpu-exp preflight --config experiment.yaml
gpu-exp run --run-id <id> --job jobs/smoke.yaml
gpu-exp status --run-id <id>
gpu-exp collect --run-id <id>
gpu-exp destroy --run-id <id>
gpu-exp reconcile --experiment-id <id>
```

상태 전이:

```text
PLANNED → PREFLIGHT_OK → CREATE_REQUESTED → POD_IDENTIFIED
 → SSH_READY → ENV_READY → RUNNING → ARTIFACTS_VERIFIED
 → DELETE_REQUESTED → DELETED_CONFIRMED → BILLING_RECONCILED
```

실패 시 원인을 남긴 뒤 결과 회수에 제한 시간을 주고 삭제 경로로 이동한다. 생성 응답을 잃은 경우 먼저 실제 자원을 조회해 대조한다. 존재 여부가 불확실한 상태에서는 재생성하지 않는다. 실행 종료와 청구 대조 완료는 별도 상태로 관리한다.

## 5. 워크로드와 비교 조건

### 고정 워크로드

- W0: 작은 텐서 연산과 CPU 기준값 비교. CUDA 인식만으로 성공 판정하지 않는다.
- W1 (기본): 모델 크기 1~5GB 범위에서 VRAM에 맞는 모델 하나로 고정 입력 추론을 수행한다. 모델 ID·revision·파일 hash, 입력 파일, 정밀도, batch size, seed, 실행 명령, 예상 출력과 허용오차를 실행 전에 한 장의 설정으로 확정한다. 비교 중에는 변경하지 않는다.
- W2 (선택): 고정 데이터·step 수·seed의 짧은 학습 또는 fine-tuning. 체크포인트 생성과 새 Pod 재개를 포함한다. 10~30GB 파일 확장도 기본 실험 이후 선택한다.

예상 단일 연산 시간은 W0 1분 미만, W1 약 1~5분, W2 약 5~15분을 목표로 조정한다. 실제 시간은 GPU별로 측정한다. 학습 재개는 모델·optimizer·scheduler·step·RNG 상태 등 해당 프레임워크에 필요한 상태를 저장한다.

Phase A에서 W1을 준비된 Pod에서 한 번 실행해 연산 기준시간을 기록한다. H1의 준비시간은 모델 로딩까지이며 추론 연산은 포함하지 않는다. 첫 유효 결과 시간에는 추론 연산을 포함한다. 최초 모델 업로드·이미지 준비 비용은 일회성 비용으로 별도 기록해 반복 실행 비용과 구분한다.

### 실험군

| 군 | 정책 | 용도 |
|---|---|---|
| K: 유지형 | 최초 생성 후 작업 사이 대기에도 Pod 유지 | 시간·비용 기준선 |
| E: ephemeral | 각 작업 직전 생성, 산출물 검증 후 삭제 | 핵심 제안 |
| B: 묶음형 (선택) | 짧은 대기에는 유지, 긴 대기에는 삭제 | K/E 결과로 필요성이 확인되면 평가 |

각 군에서 동일 GPU 모델·개수, 이미지 digest, 코드·데이터, 정밀도, batch size, 저장소 조건을 사용한다. GPU 대체는 1절의 GPU 인스턴스 제약 안에서만 허용하며, 대체가 필요하면 별도 층으로 기록하고 합쳐 평균 내지 않는다. 첫 실험은 On-demand로 제한한다.

먼저 실제 로컬 작업 2~3세션에서 GPU 작업이 필요해지는 시각을 기록해 호출 간격을 파악한다. GPU를 계속 켜둘 필요는 없다. 0·5·15·30분은 비용 계산용 탐색 구간으로 쓰고, 관측한 호출 간격에서 자주 나타나는 대기 구간 하나를 기본 K/E 비교에 사용한다. 합성 계산과 실제 청구 비교를 구분하고, 관측 범위 밖의 사용 패턴까지 결론을 확대하지 않는다.

## 6. Phase A~D

### Phase A — 기능 확인과 최소 왕복

목적: 소액으로 계정·지역·접속·저장소 경로를 검증한다.

1. 선택 GPU, 데이터센터, S3 지원, 가격, 디스크 크기, 키 종류를 확인한다. RTX 5090 기준 단가와 비교해 1절의 GPU 인스턴스 제약을 충족하는지 확인한 뒤에만 Pod를 생성한다.
2. 작은 테스트 파일을 S3로 업로드·다운로드하고 SHA-256을 비교한다.
3. Pod 한 개를 생성해 실제 연결 정보를 조회하고 SSH 비대화형 명령과 W0를 실행한다.
4. 영속 파일과 임시 파일을 의도적으로 분리해서 저장한다.
5. Pod를 삭제하고 삭제 상태를 확인한다. Pod가 없는 동안 S3 접근을 시험한다.
6. 새 Pod에서 영속 파일을 읽고 hash를 확인한다. W1 설정을 확정하고 준비된 Pod에서 기준 추론을 한 번 실행해 출력·연산시간을 기록한다. 결과 회수와 삭제 확인 후 비용 항목을 대조한다.

산출물: 기능 확인표, 설정 스냅샷, 최소 왕복 로그, 과금 내역. 실패 시 대용량 업로드와 반복 실험으로 진행하지 않는다.

### Phase B — 기동·저장소 성능과 재현성

목적: H1·H3·H4를 평가하고 반복 비용을 추정한다.

- 고정 W1을 새 Pod 3회에서 실행하고 준비시간·첫 결과 시간·결과 오차·비용을 함께 기록한다. 첫 회와 이후 회를 구분하되 provider 내부 캐시 유무를 보장하는 cold/warm 구분은 아니다.
- 기본 저장소 경로는 network volume 직접 읽기로 고정한다. 로딩이 주요 병목이면 저장소 경로 3종(매회 원격 원본 다운로드 / network volume 직접 읽기 / network volume→임시 디스크 복사)을 각 최소 3회, 순서를 섞어 추가 비교한다. H3 판정은 이 비교를 실시한 경우에만 한다.
- 3회 결과 편차가 커서 정책 판단이 어려우면 예산 안에서 3회를 추가한다. 표본을 늘린 이유를 남기고 기존 실패 기록도 유지한다.
- 이미지 pull, 설치, 파일 읽기, 모델 로딩을 분리한다. 매회 패키지 설치가 필요하면 고정 이미지 경로와 별도 비교한다.
- 같은 모델 파일을 읽어도 OS·스토리지 캐시 상태는 관측 가능한 범위만 기록한다.

산출물: 기동시간 분포, 전송량·처리량, 결과 오차, 저장소 경로 선택 근거.

### Phase C — 사용 패턴과 비용 비교

목적: H2와 묶음형 정책의 손익분기를 평가한다.

1. 실제 로컬 작업에서 기록한 호출 간격과 Phase B 실측으로 대기시간별 비용을 계산한다. 대표 대기 구간, 비교 순서, H2의 완료시간 측정 범위를 비교 전에 고정한다.
2. 대표 대기 구간 하나에서 K/E를 3쌍 비교한다. 각 정책은 같은 W1을 두 번 실행하고 그 사이에 같은 길이의 대기를 둔다. 전체 완료시간은 첫 작업 확정부터 두 번째 결과 회수까지로 하며 대기도 포함한다. 초기 생성과 마지막 삭제 비용도 양쪽에 포함하고 실행 순서를 교차한다.
3. 성공당 비용과 전체 완료시간 외에 각 GPU 호출의 대기시간도 보고한다. 긴 대기가 전체 완료시간 증가율을 작게 보이게 할 수 있기 때문이다. 평가에 사용한 반복 실행은 임계값 조정용 자료와 구분한다.
4. B가 필요하면 Phase B 자료로 유지 임계값을 고정하고, 조정에 쓰지 않은 동일 호출 일정에서 K/E/B를 3회씩 추가 비교한다. 구현하지 않았다면 B의 우월성을 주장하지 않는다.
5. W2 체크포인트 재개 3회는 학습이 실제 사용 목적일 때만 추가한다. 에이전트 추론과 GPU 계산이 겹친 시간은 이중 계산하지 않는다.

산출물: 성공 작업당 비용, 대기시간별 정책 비교, 전체 완료시간, 수작업 개입 횟수.

### Phase D — 장애 주입과 운영 문서화

목적: H5와 데이터 복구 경로를 검증한다.

기본 범위는 SSH 연결 중단과 제어기 프로세스 중단을 각 1회 시험하는 것이다. 아래 나머지 항목은 운영 필요가 생겼을 때 추가하며, 학습 중단은 W2를 선택한 경우에만 시험한다.

| 주입 상황 | 기대 동작 | 확인할 증거 |
|---|---|---|
| 생성 응답을 제어기에서 버림 | 조회·대조 후 기존 Pod 식별, 중복 생성 억제 | 생성 요청·Pod 목록·원장 |
| SSH 연결 중단 | 원격 job 상태 조회 후 재접속 또는 종료 | job ID·PID·종료코드·로그 |
| 결과 전송 중단 | 불완전 결과를 성공 처리하지 않음 | 파일 크기·hash·완료 manifest |
| 제어기 프로세스 중단 | 별도 감시기가 원장으로 정리 | 감시기 로그·삭제 확인 |
| API 접근 불가를 로컬에서 모의 | 제한적 재시도·경고·복구 후 정리 | 장애 길이·미확인 자원·초과비용 |
| 학습 프로세스 중단 | 마지막 확정 체크포인트에서 재개 | 재개 step·오차·유실 작업량 |

실서비스 장애를 유발하지 않고 실험 소유 자원과 클라이언트 측 모의 오류만 사용한다. 산출물은 실패 사례집, 복구 절차, 가설별 판정, 권장 사용 패턴이다.

## 7. 측정지표와 기록 규칙

시간은 이벤트 로그에 UTC ISO 8601로 저장하고 보고서에는 KST를 병기한다. 같은 프로세스 안의 경과시간은 monotonic clock을 사용한다. 서로 다른 호스트의 시각 차이를 확인하고, 가능하면 로컬 관측 시각으로 왕복 구간을 측정한다.

| 지표 | 정의 |
|---|---|
| T_intent_to_result | 작업 확정부터 첫 유효 GPU 결과까지. 재시도·재고 부족 포함 |
| T_api | 생성 요청 송신→응답. GPU 준비시간과 구분 |
| T_ssh | 최초 생성 요청→최초 성공한 비대화형 SSH 명령 |
| T_env | SSH 성공→의존성·모델 준비 완료 |
| T_ready | 작업 확정→모델 로딩을 마치고 추론을 시작할 준비가 된 시점. 재고 대기·재시도 포함 |
| T_work | 실제 추론·학습 구간. GPU 작업 계측 시 비동기 연산을 동기화 |
| T_persist | 작업 종료→산출물 및 manifest 무결성 검증 완료 |
| T_delete | 삭제 요청→삭제 확인. 실제 청구 종료와 별도로 기록 |
| T_agent / T_idle | 에이전트 추론 시간 / GPU를 유지했으나 job이 실행되지 않은 시간 |
| GPU 활용률 | 정해진 간격으로 표본화한 utilization·VRAM·전력. 누락 표본 수 명시 |
| 전송·I/O | 방향별 bytes, 소요시간, bytes/sec, 재전송 bytes, 모델 로딩시간 |
| 신뢰성 | 전체 시도 수, 기동·작업·보존 성공률, 중복 Pod 수, 수동 개입 |
| 비용 | 추정·청구 확정 금액, 실패 포함 총비용/유효 성공 작업 수 |
| 재현·복구 | hash 일치율, 수치 오차, 마지막 확정 step 이후 유실 step, 복구시간 |

각 단계 실패·타임아웃을 분모에서 제외하지 않는다. 기본 3회에서는 성공 횟수/전체 시도, 성공 시도 시간의 중앙값·최솟값·최댓값과 개별 측정값을 공개하고 p90을 판정 지표로 쓰지 않는다. 표본을 늘려 p90을 보고하더라도 탐색적 수치로 표시하며 실패에 임의 시간을 넣지 않는다.

학습 수치 허용오차는 실행 전 정한다. 예: 고정 입력 출력의 absolute/relative tolerance 또는 최종 loss 범위. GPU 비결정성이 있는 연산에서 byte 단위 결과 일치를 강제하지 않는다. 저장 파일의 전송 무결성은 수치 재현성과 별개로 SHA-256으로 판정한다. multipart ETag를 SHA-256으로 간주하지 않는다.

## 8. 비용모델과 예산

가격은 하드코딩하지 않는다. GPU 가격은 `cache/gpu-prices.json`에 GPU 종류·데이터센터·과금 방식·통화·조회 시각과 함께 저장하고 24시간 재사용한다. 매 생성마다 전체 가격을 다시 조회하지 않는다. 캐시 만료나 명시적 갱신 요청 시 다시 조회하고, 배포 응답의 실제 단가가 캐시와 다르면 해당 실행에 기록해 가격 상한을 재검증한다. 재고는 가격 캐시와 분리해 필요한 시점에 조회한다. 디스크·network volume 단가도 출처와 함께 기록하고 표기 GB와 실제 bytes/GiB를 구분한다.

```text
C_total = C_gpu + C_ephemeral_disk + C_network_volume
          + C_external_storage_and_transfer + C_agent + C_tax_or_other

C_gpu = Σ (GPU별 시간당 단가 × GPU 개수 × 청구시간[초] / 3600)
C_storage_est = Σ (할당 GB × 월 단가 × 보존시간 / 해당 견적의 월 환산시간)
C_per_success = 실패·재시도 포함 C_total / 유효 성공 작업 수
Savings = 1 - C_ephemeral / C_keep
```

저장소 비용은 사용량인지 할당 용량인지 실행 전 확인한다. 월 환산시간과 최소 과금·반올림은 제공자 기준에 맞춘다. Network volume은 실험 사이와 Pod 삭제 후의 보존기간도 계산한다.

공식 Pod 가격 페이지는 network volume을 시간 단위, container/volume disk를 초 단위로 설명하지만 Billing overview는 전체를 초 단위로 요약한다. 세부 과금 단위는 두 문서가 일치하지 않으므로 임의 확정하지 않고 실제 내역으로 대조한다. [가격 문서](https://docs.runpod.io/pods/pricing), [과금 개요](https://docs.runpod.io/accounts-billing/billing)

현재 가격 문서는 RunPod ingress/egress 요금이 없다고 안내한다. 외부 원본 저장소·백업·인터넷 회선 비용까지 0이라는 뜻은 아니므로 별도 확인한다. 충전액은 자원 사용비용과 구분한다. [공식 가격](https://docs.runpod.io/pods/pricing)

### 유지·삭제 손익분기

```text
ΔC_restart = 재생성·재로딩·추가 복사·실패 위험의 추가비용
Δr_idle = 유지할 때와 삭제할 때의 시간당 비용 차이
대기 손익분기[시간] = ΔC_restart / Δr_idle   (Δr_idle > 0일 때)
```

양쪽에서 동일하게 유지하는 network volume 비용은 차액에서 상쇄하되 총비용에는 남긴다. 재시작 대기시간에 대한 사용자 가치가 필요하면 별도 시간비용 계수를 적용한다. GPU 가용성 손실도 기록해 단순 요금 절약과 구분한다.

계산 예시일 뿐 실제 견적은 아니다: 단일 GPU 비용이 $0.50/h, 추가 재기동 청구시간이 3분, 나머지 차액이 0이면 재기동 비용은 $0.025이고 대기 손익분기는 3분이다. 15분 대기는 유지 비용 $0.125 대비 $0.10 절약 가능하지만 실제 디스크·실패·가용성 비용을 더하면 결과가 달라진다.

### 초기 예산 제안

| 구간 | GPU·임시 디스크·실패분 예산 |
|---|---:|
| Phase A | $2 |
| Phase B | $6 |
| Phase C | $8 |
| Phase D | $4 |
| 소계 | $20 |

Network volume 보존·외부 백업·에이전트·세금 예산은 별도 항목으로 사전 입력한다. 단가상 위 표로 최소 표본을 충족할 수 없으면 먼저 표본·모델·GPU를 조정하고 근거를 남긴다. 예산을 맞추려고 실패 시도를 삭제하지 않는다.

위 $20은 기본 실험의 잠정 GPU·임시 디스크 예산이며 충분성이 검증된 금액은 아니다. Phase A 종료 후 `실행 횟수 × (기동 + 연산 + 결과 보존 + 유지형 대기 + 정리 여유)의 예상 청구시간 × 단가`로 남은 비용을 다시 계산한다. 일회성 준비비와 저장소 보존비도 별도 합산한다. 선택 실험은 남은 예산 안에서만 추가하며, 예산 부족 시 미실시로 남긴다.

실행 전 `이미 쓴 금액 + 활성 자원의 만료까지 예상 비용 + 새 실행 최악 비용 + 정리 여유 비용`을 계산해 전체 예산을 초과하면 생성하지 않는다. 청구 반영 지연 때문에 잔액 조회만을 hard cap으로 사용하지 않는다.

## 9. 안전장치

1. **자원 소유권:** experiment_id/run_id와 Pod ID를 로컬 원장에 저장한다. 제공자 태그를 쓸 수 있으면 보조로 사용한다. 정리는 원장·소유권이 일치하는 자원만 대상으로 한다.
2. **동시 실행 제한:** 1차 실험은 활성 Pod 최대 1개. 생성 잠금과 원장 갱신을 사용하며 불확실한 생성 응답에서 무조건 재시도하지 않는다.
3. **만료와 감시:** 실행별 최대 수명과 전체 실험 마감시각을 미리 정한다. 예: smoke 10분, W2 30분. 별도 감시기를 실험 전에 시험하며 동일 PC 장애·절전 시 함께 멈출 수 있음을 기록한다.
4. **실패 종료:** 연결·환경·job·회수 각각 타임아웃과 최대 재시도를 둔다. 회수 실패로 무기한 GPU를 유지하지 않고 제한 시간 후 손실 내용을 기록하고 삭제한다. 중요한 작업은 실행 중에도 체크포인트를 영속화한다.
5. **삭제 증거:** 삭제 호출 성공만으로 완료 처리하지 않는다. API 조회 또는 목록에서 삭제 상태를 확인하고 나중에 청구 내역을 대조한다. 잔여 저장소는 별도 목록으로 보고한다.
6. **자격증명:** 제어 API 키는 로컬 제어기에 두고 GPU Pod에 전달하지 않는 것을 기본으로 한다. 비밀은 Git·로그·명령 인자·이미지에 넣지 않는다. SSH 공개키만 등록하고 비밀번호 없는 공개 서비스는 열지 않는다.
7. **무결성:** 모델은 content hash별 불변 경로, 결과는 run_id별 경로를 쓴다. 업로드 후 크기와 다운로드 hash를 확인한 뒤 완료 manifest를 마지막에 공개한다. 이는 애플리케이션 규칙이며 원자적 트랜잭션 보장이 아니다.
8. **단일 writer:** 같은 모델·체크포인트를 S3와 Pod에서 동시에 덮어쓰지 않는다. 미완료 파일은 별도 경로에 두며 실패 업로드 정리 기능도 지원 확인 후 사용한다.
9. **백업과 잔액:** 중요한 체크포인트는 로컬 또는 독립 저장소에도 보관하고 복원을 시험한다. Network volume은 백업과 동일하지 않다. 잔액 고갈을 종료 장치로 쓰지 않는다. 잔액 부족으로 저장소까지 손실될 수 있다. [공식 저장소 문서](https://docs.runpod.io/storage/network-volumes)
10. **환경 고정:** 이미지 digest, 코드 commit, 의존성 lock, CUDA·프레임워크·드라이버 버전을 기록한다. 새 호스트 드라이버가 동일할 것이라 가정하지 않는다.

## 10. 저장소 구조

아래는 구현할 실험 저장소 구조이며, 이 문서와 함께 코드가 구현되었다는 뜻은 아니다.

```text
runpod-ephemeral-lab/
├─ README.md
├─ experiment.yaml              # 예산·시간제한·GPU·스토리지 선택, 비밀 없음
├─ .env.example                # 변수 이름만
├─ .gitignore                  # 비밀·개인 원장·대형 파일 제외
├─ container/Dockerfile
├─ requirements.lock
├─ controller/                 # 생성·연결·실행·삭제·대조
├─ watchdog/                   # 독립 감시·기한 초과 정리
├─ jobs/{smoke,inference,train}.yaml
├─ scripts/                    # bootstrap, hash, checkpoint 검증
├─ manifests/                  # 모델·데이터 출처/라이선스/hash
├─ records/<run_id>/
│  ├─ config.json              # 민감정보 제거한 설정
│  ├─ events.jsonl
│  ├─ metrics.json
│  ├─ artifacts.json
│  └─ billing.json
├─ private/                    # Git 제외, 자원 원장·연결정보
└─ reports/                    # 분석·결론·실패 사례

network-volume-root/
├─ models/<sha256>/...
├─ datasets/<sha256>/...
└─ runs/<run_id>/
   ├─ incomplete/...
   ├─ checkpoints/<step>/...
   ├─ outputs/...
   └─ manifest.complete.json
```

대형 파일은 Git에 넣지 않는다. Manifest에는 파일 경로·bytes·SHA-256·원본 출처·버전을 기록한다. 원장과 작은 로그는 Pod 외부에 즉시 보존한다.

## 11. 실행 순서

1. GPU 종류·VRAM 요구·작업·허용오차·예산·저장소 보존기한을 채운다.
2. 공식 문서와 콘솔에서 API/CLI 버전·지원 지역·가격·SSH 경로를 확인하고 기록한다.
3. 로컬에서 코드·입력·이미지를 확정하고 가능한 테스트를 완료한다.
4. 비밀 주입, 원장, 타임아웃, 감시기, 삭제 경로를 구현·점검한다.
5. Phase A를 실행한다. 작은 파일 왕복·삭제·새 Pod 복원이 모두 통과해야 다음 단계로 간다.
6. 모델·데이터를 사전 업로드하고 manifest를 검증한다. GPU 없이 가능한 작업을 먼저 끝낸다.
7. Phase B를 실행하고 기동·저장소 경로를 측정한다.
8. 예산 잔여와 예상 비용을 검토하고 Phase C의 쌍 비교 순서를 고정한다.
9. Phase C와 D를 실행한다. 매회 정상·실패 모두 결과 회수와 삭제 확인으로 마무리한다.
10. 전체 Pod 목록과 원장을 대조하고 남은 volume·디스크·기타 유료 자원을 목록화한다.
11. 청구 반영 후 추정값을 대조하고 H1~H5를 통과/미통과/판단 유보로 판정한다.
12. 백업 검증 후 보존기한에 맞춰 실험 저장소를 정리한다. 공유 volume은 삭제하지 않는다.

## 13. 완료 조건

- Phase A~D의 기본 범위 실행 기록과 실패 기록을 모두 보존했다. 선택 실험은 실시 여부와 이유를 남겼다.
- H1~H5 각각에 측정값 또는 판단 유보 이유가 있다.
- 불필요한 Pod가 없고, 남긴 유료 저장소의 목적·예상 비용·정리일이 명확하다.
- 중요 산출물을 독립 위치에서 복원했고 hash를 확인했다.
- 다른 사람이 고정 설정과 실행 순서만으로 같은 사용 패턴을 재현할 수 있다.

최종 권장 정책은 실측으로 정한다. 재생성 비용보다 대기비용이 큰 구간은 삭제하고, 짧은 반복 작업은 묶어서 실행하며, 재고 부족이나 모델 로딩이 지배적인 환경은 유지형의 시간상 이점도 함께 보고한다.
