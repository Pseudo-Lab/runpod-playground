# ACE-Step 1.5 음악 생성으로 재검증

2026-10-24 사전 설계. 기존 Qwen 실험과 파일을 보존하며 별도 `records/ace-step/`에 기록한다. 모델이 작고 출력이 짧았던 기존 주장의 적용 범위를 실제 60초 음악 생성으로 다시 확인한다. 결과가 불리해도 그대로 게시한다.

## 고정 구성

- GPU: 실제 RTX5090, EU-RO-1, 생성 전 견적 재확인. GPU 단가는 기존 5090 기준 $1.19/h를 넘지 않는다. 동시 GPU 1개, 별도 자원비 예산 $6, Pod 수명 최대 40분, 전체 자원 만료 4시간, 독립 watchdog.
- 코드: 공식 `ace-step/ACE-Step-1.5`, commit `ca1e85fe9430179831e6bc6be790c332190a3866`.
- 기본 체크포인트: `ACE-Step/Ace-Step1.5`, revision `19671f406d603126926c1b7e2adc169acbcade22`.
- 언어모델: `ACE-Step/acestep-5Hz-lm-4B`, revision `0a3ec94b557aea7d508da38b31cfe7341f6ff737`.
- 음악 생성: turbo 2B DiT + 4B 5Hz LM + 공식 VAE + Qwen3 텍스트 인코더. `thinking=True`, batch 1, 길이 60초, 8 diffusion steps, seed 42. 영문으로 서술한 오리지널 instrumental lo-fi jazz hip-hop, 100 BPM, D minor, 4/4. 기존 곡이나 특정 아티스트 모방을 요구하지 않는다.
- 공식 uv.lock으로 환경을 준비하되 flash-attn은 설치하지 않는다. LM은 공식 nano-vllm의 SDPA/eager 경로를 요청하고 실제 선택된 backend를 기록한다. flash attention·CUDA graph·torch.compile 최적 성능의 벤치마크로 주장하지 않는다. 설치 문제의 변경은 변경 내역과 소스 hash를 남긴다.
- 실행환경과 모델은 전용 60GB network volume에 보관한다. 설치·의존성 재사용 방식이 이전 Qwen의 작은 tar와 달라 단일 하드웨어 효과로 비교하지 않는다. 기본 모델 저장소가 포함하는 사용하지 않는 기본 1.7B LM까지 받은 경우 다운로드·저장량에 포함하되 실제 사용한 모델과 구분한다.

## 첫 준비와 새 Pod 재사용

1. 빈 volume에서 소스·실행환경·고정 모델을 준비하고 실제 FLAC 음악을 생성한다. 최초 생성 요청부터 로컬 결과 파일의 회수·검증까지 연속 측정한다. 설치, 다운로드, hash 검증, import·모델 초기화, 생성, 파일 회수를 별도 기록한다.
2. GPU를 삭제한 상태에서 S3로 작은 표식 왕복, 대형 가중치 HEAD와 64KB Range hash를 확인한다. S3는 RunPod network volume의 호환 API이며 AWS S3가 아니다. 전체 대형 파일의 S3 왕복은 주장하지 않는다.
3. 같은 volume에서 새 Pod 3개를 순차 생성하고 각각 같은 60초 음악을 생성해 로컬로 회수한다. 매번 사용한 가중치 전체 SHA-256을 대조한다. 새 Pod ID와 GPU 종류를 기록하되 물리 호스트 이동과 공급자·OS 캐시는 통제하지 못한다.
4. 준비된 첫 재사용 Pod에서 추가 생성 3회로 상주 상태의 반복 생성시간을 관측한다. 초기 생성과 반복의 차이를 보존한다. 음질·모델 간 품질 우열을 평가하는 블라인드 시험은 아니다.

음악 파일은 실제 sample rate, channel 수, 길이, 유한한 sample, RMS·peak·clipping 비율과 SHA-256을 확인한다. seed가 같아도 GPU 커널과 LM 샘플링으로 음악이 완전히 같다고 가정하지 않는다. PCM hash와 실제 차이를 보고하며, 출력이 유효한지와 bitwise 재현되는지는 구분한다. 성공 음원 일부는 블로그와 슬라이드에서 직접 재생할 수 있게 보존한다.

## 실제 보존·반납 정책

상시 보존, 즉시 반납, 고정 TTL 20초, 예측 TTL 네 가지를 실제 Pod 삭제·재생성으로 비교한다. 각 정책에서 첫 GPU는 모델 준비 완료로 시작한다. 공통 최초 준비는 정책 비교에서 제외하지만 전체 비용에는 포함한다. seed 20261025로 정책 순서를 고정한다. 정책당 한 번의 설명용 소표본이다.

사용자는 결과를 받은 뒤 다음 시도를 한다고 가정한다. 네 번의 60초 음악 생성을 하고, 응답 회수 이후 각각 5·25·180초를 쉰다. 마지막 응답 뒤 35초를 관측한다. 모든 정책에서 같은 생성 횟수와 생각할 시간을 사용한다. 정책에 따라 응답이 달라지므로 실제 요청 도착시각도 달라진다. 기존 Qwen의 고정 시각 요청열이나 대기열 부하와 같은 실험으로 취급하지 않는다.

예측기는 **응답 완료부터 다음 요청까지의 think time**을 관측한다. EWMA 초기값 10초, alpha 0.5, TTL=min(60,max(5,4×EWMA))초. 요청이 도착한 뒤에만 과거 공백을 갱신하며 미래 공백을 미리 주지 않는다. 긴 간격을 예상해 오래 기다리는 이 규칙은 비용 최적 정책이 아니라 사전 고정한 단순 휴리스틱이다. 대기열이 비고 실행 중인 요청이 없을 때에만 삭제한다. 모델·체크포인트는 지우지 않는다.

주요 결과는 전체 세션의 요청별 응답시간·평균·최댓값·전체 완료시간, 생성 요청부터 삭제 확인까지의 보유 근사시간, 그 기반 비용 추정, 재기동 횟수다. 정확한 공급자 과금과 제어기 구간은 다를 수 있다. 보존비용과 대기시간을 임의의 시간 가치로 하나의 점수에 합치지 않는다. 단발 실행이므로 정책의 통계적 우월성이나 실제 사용자 p95를 주장하지 않는다.

## 해석과 종료

새 ACE-Step 실험과 과거 Qwen·L4 결과를 다른 층으로 표시한다. 작은 합성 Transformer 복구는 ACE-Step 학습 재개 실험으로 바꾸어 쓰지 않는다. 정확한 코드와 모델 버전, 환경 freeze, 원자료, 실패와 수정을 보존한다. 모든 음원을 로컬로 회수한 뒤 GPU와 volume을 모두 삭제하고 현재 유료 자원 수와 시간당 사용액을 확인한다. 비용은 견적 기반 추정이며 세금·에이전트 비용 및 확정 청구와 구분한다.
